    11 - PostgreSQL 持久化集成¶

    版本：v1.0 |最后更新：2026-07-15 |状态：批准设计 依赖关系：03 - Business Logic & Persistence、06 - Phase Roadmap

    1. 目的¶

    当前服务器具有完整的 Drizzle 架构、生成的迁移、种子脚本和 PostgreSQL 客户端。运行时域服务仍然直接读写单例InMemoryStore。本文档定义了使 PostgreSQL 成为持久生产后端的最小安全路径，同时保留单元测试和显式本地开发的内存中实现。

    这是增量迁移。它没有引入并行的、部分功能的持久性路径。

    2. 决定¶

    决定 理由
    PostgreSQL 在生产中是必需的。 进程本地映射在重新启动时会丢失所有状态，并且无法支持多个服务器实例。
    内存持久性仅适用于 development 和 test。 它使单元测试保持快速并支持无需基础设施的隔离本地工作。
    域服务依赖于异步、查询形状的持久性端口。 PostgreSQL 是异步的；接口必须表示有用的域查询，而不是公开 Map 操作。
    一次迁移一个垂直域切片。 服务、其路由、WebSocket 调用者和测试一起移动。这限制了行为风险并避免了回购范围内的卖旗日。
    在运行时选择 PostgreSQL 适配器之前先实现它。 空的 Drizzle 存根和 PERSISTENCE=postgres 开关将创建一个可启动但无法提供流量的配置。
    事务属于服务用例边界。 存储库不得使跨表操作部分持久。
    PostgreSQL 仅存储持久事实。 存在、速率限制、机器人交付队列和开发文件字节具有不同的生命周期和扩展要求。

    3. 当前差距¶

    apps/server/src/db/client.ts 导出 pg.Pool 和 Drizzle 客户端，但运行时代码不会查询它。以下代码路径直接访问InMemoryStore：

    • 域服务：身份验证、工作区、消息、附件、机器人和信号。
    • HTTP 路由：通道修补、反应广播和开发上传/下载端点。
    • WebSocket 网关和套接字服务器：机器人响应查找、房间引导和存在引用计数。

    该模式还需要协调才能忠实地保留当前行为。特别地，当前运行时模型包含通道createdById、description和deletedAt；消息回复和转发元数据；已保存的消息；阅读收据；频道静音；固定消息；文件channelId；以及迁移尚未完全建模的读取状态表示。

    4.持久化边界¶

    4.1 形状¶

    每个服务仅接收其所需的持久端口。端口使用域类型并返回两种实现的承诺。它们不公开 Drizzle 表、pg.Pool、Maps 或通用 CRUD 方法。

    HTTP routes / WebSocket gateway
              |
              v
        Domain service
              |
              v
       Persistence port
       /               \
In-memory adapter   PostgreSQL adapter
       |                    |
  InMemoryStore       Drizzle + PostgreSQL

    组合根从适配器创建服务。仅在迁移每个服务时，它才替换模块级服务单例。现有的未迁移服务继续使用store；这可以最大限度地减少过渡期间的变化。

    type MessagePersistence = {
  getChannelForSend(channelId: string, actorId: string): Promise<Channel | undefined>;
  getMessage(id: string): Promise<Message | undefined>;
  findBySenderClientMessageId(senderId: string, clientMsgId: string): Promise<Message | undefined>;
  createMessage(input: NewMessage): Promise<Message>;
  listPage(input: MessagePageQuery): Promise<MessagePage>;
  updateMessage(input: MessageUpdate): Promise<Message>;
  transaction<T>(work: (tx: MessagePersistence) => Promise<T>): Promise<T>;
};

    该示例是特意设计成查询形状的。 listPage、findBySenderClientMessageId 和 getChannelForSend 直接映射到索引 SQL 查询。诸如 getAllMessages() 或 setMapValue() 之类的接口将保留 Map 实现，而不是将服务与其分离。

    4.2 交易规则¶

    当用例更改多个持久关系时，服务拥有一个事务：

    使用案例 交易内容
    注册 创建用户，追加注册审核记录
    创建工作区 工作区、所有者会员资格、general 频道、创建者会员资格
    创建DM 查找/创建确定性 DM 和两个成员资格，受唯一性约束保护
    发送消息 幂等性查找/插入、附件关联、持久审计/事件记录（如果引入）
    删除工作区成员 会员删除和相关频道会员删除
    消费信号预密钥 选择一个未使用的带行锁的键并将其标记为已消耗

    PostgreSQL 信号适配器必须使用带有 FOR UPDATE SKIP LOCKED 的事务来进行一次性预密钥分配。在并发请求下，先读取后进行独立更新并不安全。

    4.3 非持久状态¶

    以下是特意在 PostgreSQL 存储库端口之外的内容：

    状态 目标所有者
    在线连接计数和打字指标 Redis/Socket.IO单节点阶段的进程状态； Redis 多实例部署
    WebSocket 和身份验证速率限制桶 Redis
    机器人待处理事件队列 Redis Streams 或 BullMQ，而不是 BotIntegration 上的 JSON 数组
    三秒读回执批处理缓冲区 Redis 或进程本地缓冲区，其刷新通过消息/读取状态端口持续存在
    开发上传字节 仅供开发Map；生产使用对象存储
    指标和瞬态 WebSocket 事件可观测性和传输层

    这些问题不得隐藏在 PresenceRepository、DevFileRepository 或通用存储库聚合中。它们是操作状态，而不是关系域记录。

    5. 架构协调¶

    在实现任何 PostgreSQL 适配器之前，请更新 apps/server/src/db/schema.ts、生成新的迁移并验证干净的数据库。现有的 0000 迁移是一个基线，并不能证明所有当前运行时功能都是可持久的。

    所需核对项目：

    当前行为 所需的关系表示
    频道创建者、描述、软删除 将 created_by_id、description 和 deleted_at 添加到 channels。
    回复和转发元数据 根据共享 Message 类型的要求，将 reply_to_message_id、original_sender_id 和 original_created_at 添加到 messages。
    已保存的消息 添加带有组合键 (user_id, message_id) 的 saved_messages。
    已读回执和未读状态 添加message_read_receipts；使用与 API 语义匹配的时间戳或游标表示 channel_members 上每个通道的上次读取状态。不要维护单独的仅内存中的 channelLastRead 事实来源。
    针脚 添加带有通道/消息复合键的 channel_pins 并以事务方式强制执行 50-pin 限制。
    频道静音首选项 添加 channel_mutes 和 (user_id, channel_id) 组合键。
    文件通道关联 将可为空的 channel_id 添加到 files，匹配 FileRecord。
    机器人交付 在 PostgreSQL 中保留机器人集成、会员资格和订阅记录；将挂起的事件传递移至 Redis Streams/BullMQ。

    该实现还必须在 PostgreSQL Date 值和共享域合约使用的 ISO 字符串之间定义显式映射器。 Drizzle 行类型不会从适配器泄漏到域服务中。

    6. 运行时配置和生命周期¶

    6.1 配置¶

    添加 PERSISTENCE=memory|postgres 并使用现有 Zod 环境架构对其进行验证。

    • development和test：当PERSISTENCE不存在时，默认为memory。
    • production：需要PERSISTENCE=postgres；在环境验证期间拒绝 memory。
    • Docker Compose 类似生产的配置集 PERSISTENCE=postgres、DATABASE_URL=postgres://...@postgres:5432/nexus_chat，并等待 PostgreSQL 运行状况。
    • SESSION_STORE=redis是独立选择的。持久性选择不得默默地更改会话存储。

    当选择PostgreSQL时，必须要求DATABASE_URL。当数据库不可用时，不会自动回退到内存。

    6.2 客户端生命周期¶

    数据库模块拥有一个延迟创建的 pg.Pool、Drizzle 实例及其生命周期：

    1. 组合根仅在PERSISTENCE=postgres时初始化PostgreSQL。
    2. 在接受流量之前，它会运行 SELECT 1 准备情况检查。
    3. 迁移在 CI/CD 或显式一次性迁移作业中运行，而不是默认在每个应用程序进程中运行。
    4. 可能支持仅限本地的 DB_MIGRATE_ON_BOOT=true，但生产启动时迁移仍处于禁用状态。
    5. SIGTERM和SIGINT首先停止HTTP服务器，然后关闭池。

    /healthz 应报告进程活跃度。添加 /readyz 以实现依赖准备：当配置的 PostgreSQL 或 Redis 依赖不可用时，它会报告失败。

    7. 迁移顺序¶

    每个编号的步骤都是可独立构建、可测试和可部署的。不要在使用未使用的存储库文件或 Drizzle 占位符的切片之前添加它们。

    步骤 0：基础设施和模式奇偶校验¶

    • 在 docker-compose.yml 中启用 PostgreSQL 和 Redis 服务，并进行命名 PostgreSQL 卷和运行状况检查。
    • 将显式迁移和种子命令添加到本地/CI 工作流程。
    • 协调第 5 节中的架构，生成新的 Drizzle 迁移，并从空数据库测试迁移。
    • 添加数据库准备情况和正常池关闭。

    此步骤不会将 PERSISTENCE=postgres 添加到实时服务选择中。

    第 1 步：验证垂直切片¶

    • 仅定义身份验证所需的 UserPersistence 和 AuditPersistence 端口。
    • 针对 InMemoryStore 实施并测试内存适配器。
    • 针对一次性 PostgreSQL 数据库实施和集成测试 PostgreSQL 适配器。
    • 在需要时将 authService 公共方法转换为异步方法；仅更新身份验证路由和受影响的身份验证中间件调用者。
    • 在组合根中选择适配器并使生产​​使用 PostgreSQL。

    步骤 2：工作空间和通道垂直切片¶

    • 定义工作区/成员/通道访问和突变的端口。
    • 将工作区创建、所有权转移、成员资格变更、通道生命周期、确定性 DM 创建、静音和通道更新移至这些端口后面。
    • 使用事务来创建工作区、创建 DM 和删除成员。
    • 更新房间引导程序以查询服务级别工作区/通道访问而不是迭代store。

    步骤 3：消息垂直切片¶

    • 定义查询形状的消息、反应、保存的消息、附件引用、pin 和读取状态端口。
    • 将幂等性移至 PostgreSQL 唯一的 (sender_id, client_msg_id) 约束。发生冲突时，获取并返回现有消息。
    • 使用与共享 API 协定相匹配的排序和光标格式来实现光标分页。
    • 更新 HTTP 消息路由和 WebSocket 网关以等待消息服务。
    • 将短期收据批处理保留在持久适配器之外，然后通过事务持久性方法进行刷新。

    步骤 4：附件、信号和机器人¶

    • 附件：在 PostgreSQL 中保存元数据和上传会话；将字节存储留在开发Map中，直到引入对象存储。
    • 信号：实现事务性一次性预密钥分配和持久不透明会话元数据。
    • 机器人：持久安装、会员资格和订阅；将pendingEvents替换为多实例部署前选择的队列机制。

    步骤 5：删除直接商店访问权限¶

    • 用迁移的服务或显式瞬态基础设施替换路由和 WebSocket 代码中剩余的直接 store 导入。
    • 限制 InMemoryStore 导入到内存适配器和测试实用程序。
    • 仅使 PERSISTENCE=memory 成为有意的开发/测试模式。

    8. 测试策略¶

    测试级别 后端 目的
    单位 内存适配器 无需基础设施的快速服务规则和故障路径。
    适配器集成 一次性 PostgreSQL 验证 SQL、映射、约束、事务和迁移。
    路由/WebSocket 集成 PostgreSQL 在需要时加上 Redis 验证异步传播、授权、幂等性和广播。
    迁移烟雾 清空 PostgreSQL 数据库 应用所有迁移并运行种子数据。

    存储库接口是通过服务行为来测试的，而不是通过断言内部 Map 副作用来测试。 PostgreSQL 适配器测试必须包括重复消息传递、并发 DM 创建、工作区创建回滚以及并发一次性预密钥消耗。

    9. 非目标¶

    • 不要创建通用 CRUD 存储库、全局存储库注册表或在运行时抛出的适配器框架。
    • 不要将 Redis 拥有的操作状态迁移到 PostgreSQL。
    • 不要在每个服务器副本上自动运行生产迁移。
    • 不要仅仅为了使其类似于当前地图而更改域行为；在关系模式和生产需求需要时正确的持久化语义。
    • 在 PostgreSQL 支持的服务和适配器集成覆盖范围存在之前，请勿删除内存适配器。

    10. 验收标准¶

    1. 如果 PostgreSQL 未配置或不可用，则在提供流量之前生产启动会失败。
    2. 开发和测试模式可以显式使用内存持久化，无需创建数据库池。 3.每个迁移的垂直切片都有完整的内存适配器、PostgreSQL适配器、服务布线和PostgreSQL集成测试。
    3. 没有生产配置的请求路径从InMemoryStore读取持久数据。
    4. 架构迁移代表每个迁移的运行时字段和约束。
    5. 多行突变和一次性预密钥消耗是原子的。
    6. pnpm lint、pnpm typecheck、pnpm test 和 pnpm build 在每个切片之后传递。

    附录：对先前基金会提案的更正¶

    之前的提案更正如下：

    • 它不再在服务使用所有存储库和非功能性 Drizzle 实现之前创建它们。
    • 它不会将 getAllMessages() 等 Map 型方法公开为预期的 PostgreSQL 边界。
    • 它从 PostgreSQL 存储库范围中删除存在、开发文件字节和机器人待处理事件数组。
    • 在 PostgreSQL 选择之前需要架构奇偶校验，而不是假设现有迁移涵盖所有运行时行为。
    • 它需要在生产中使用 PostgreSQL，而不是将 PERSISTENCE=memory 作为生产默认值。
    • 默认情况下，它将迁移移至部署作业，并分别添加就绪性和活动性。
