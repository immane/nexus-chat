    1. 系统概述¶

    1.1 项目愿景¶

    Nexus Chat 是一个类似 Slack 的即时消息 (IM) 平台，构建为 Electron 桌面应用程序、第一阶段终端 UI 客户端和 Node.js 后端。它支持工作区、通道、直接消息 (DM)、线程对话、文件共享和可扩展的机器人框架 - 所有这些都作为 SaaS 多租户云部署 提供。

    1.2 核心优势：混合加密模式¶

    Nexus Chat 中的每个通道和 DM 都以两种加密模式之一运行，可以在创建时选择：

    模式 标签 能力 限制
    正常 normal 完整的 IM 功能 + Bot 集成 + 服务器端搜索/索引 服务器可以读取消息
    端到端加密 e2e 仅限 IM（文本、附件）、只读/消失的消息；服务器是不透明中继 无机器人参与；没有服务器端搜索；没有消息预览

    混合模型的主要设计含义：

    • 普通通道允许机器人参与对话、执行斜杠命令并对消息事件做出反应。服务器以明文形式处理和存储消息内容（通过 PostgreSQL TDE 或文件系统加密进行静态加密）。
    • E2E 通道 使用 Signal Protocol (@signalapp/libsignal)。服务器只能看到密文 blob、加密元数据和只读/消失消息的生命周期策略元数据。密钥交换、棘轮推进和消息解密仅发生在客户端上。服务器的角色被简化为存储转发中继加上逻辑删除/过期强制执行，而无需明文访问。
    • 单个工作区可以并排包含普通通道和 E2E 通道。模式徽章在频道侧边栏中可见。

    详细的端到端威胁建模和信号协议集成设计请参见Security & E2EE Roadmap。

    1.3 多租户SaaS架构¶

    该平台遵循标准 SaaS 多租户模型：

    • 租户映射到工作空间 - 一个包含用户、通道、机器人和文件的独立命名空间。
    • 工作区数据在应用程序层逻辑上分离（使用 workspaceId 外键的工作区范围查询）。第 1 阶段没有使用每个租户共享数据库策略（所有租户使用单个 PostgreSQL 集群）。
    • 身份验证是工作区范围的：用户可能属于多个工作区并在客户端中在它们之间切换。

    分层职责¶

    层 责任 关键部件
    客户端外壳 桌面运行时、本机操作系统集成、离线持久性、Signal Protocol E2EE 客户端 Electron 主进程、预加载桥、Zustand 存储、IndexedDB
    核心网关 身份验证、请求验证、WebSocket 连接管理、速率限制、消息路由 Hono HTTP 服务器、Socket.IO 服务器、用于水平 WebSocket 扩展的 Redis 适配器
    业务逻辑后端 用于身份验证、工作区、通道、消息、信号密钥分发、附件生命周期和机器人事件路由的域逻辑。机器人可以启动工作流程，但核心拥有持久性、授权、索引、加密边界和生命周期关键状态。 服务模块、Drizzle ORM、PostgreSQL、Redis 缓存层、附件服务
    异步机器人引擎 解耦的机器人生命周期、事件驱动的消息处理、多语言机器人SDK、流媒体中继、内置机器人（@AIBot、@FileBot、@WelcomeBot 等）、第三方机器人托管 Redis Streams 消费者组、BullMQ 每个机器人队列、机器人 WebSocket 连接、斜杠命令路由器、块批处理器

    4. 技术栈总结¶

    层 技术 版本 理由
    桌面外壳 电子 ^42.5 跨平台桌面、成熟生态、原生操作系统集成
    用户界面框架 React 19 + Vite 7 ^19.0 / ^7.0 并发功能（useTransition、useDeferredValue）、快速 HMR、ESM 原生
    构建集成 vite-插件-电子 ^1.0.4 灵活的Vite+Electron集成，支持多环境模式，不Bundle实现快速HMR
    状态管理 祖斯坦 ^5.0 轻量级、选择器精度渲染、基于Map的标准化存储、中间件生态系统
    造型 Tailwind CSS v4 + CVA ^4.0 / ^0.4 实用程序优先，具有 CSS 变量设计标记，class-variance-authority 用于组件变体
    虚拟滚动 反应大师 最新 内置双向无限滚动、自动跟随输出、粘性组标题

    5. 数据流程图¶

    5.1 普通模式消息流¶

    Sender Client                  Gateway/Server                   Recipient Client(s)
     │                              │                                  │
     │ 1. message:send ────────────→│                                  │
     │    {channelId, clientMsgId,  │                                  │
     │     content}                 │                                  │
     │                              │ 2. Auth + Rate Limit Check       │
     │                              │ 3. Idempotency Check (Redis)     │
     │                              │ 4. Validate Content (Zod)        │
     │                              │ 5. INSERT INTO messages          │
     │                              │    (assign server ID, UUID v7)   │
     │ 6. message:ack ─────────────│                                  │
     │    {messageId, status:      │                                  │
     │     "sent"}                  │                                  │
     │                              │ 7. Cache → Redis (ZADD hot)      │
     │                              │ 8. Publish Event → Redis Streams │
     │                              │ 9. Bot Engine consumes event     │
     │                              │    (if channel has bots)         │
     │                              │10. message:new ─────────────────→│
     │                              │    {full Message object}         │
     │                              │                                  │
     │                              │11. ← message:delivered ─────────│
     │                              │    {messageId, userId}           │
     │12. ← message:delivered ─────│                                  │
     │                              │                                  │
     │                              │13. ← message:read ──────────────│
     │                              │    {channelId, userId,           │
     │                              │     lastReadMessageId}           │
     │14. ← message:read ──────────│                                  │
     │                              │15. Read Receipt Aggregator       │
     │                              │    (buffer 3s → batch UPSERT)    │

    主要特征：

    • 服务器是消息 ID 的真实来源（UUID v7，按时间排序）。
    • clientMsgId提供幂等性：如果由于网络问题重试相同的消息，服务器将通过Redis进行重复数据删除（dedup:{clientMsgId}）。
    • 消息以明文形式存储在 PostgreSQL 中（服务器可读）。对于正常模式，可以进行服务器端搜索和机器人参与。
    • 读取回执会聚合在 3 秒缓冲区中，然后批量插入到 PostgreSQL 以避免写入放大（请参阅IM Backend Research §3.5）。
    • 机器人引擎通过 Redis Streams 接收每个消息事件的副本。机器人可能会异步响应。

    5.2 端到端模式消息流程¶

    Sender Client                  Gateway/Server                   Recipient Client(s)
     │                              │                                  │
     │ 1. Encrypt locally:          │                                  │
     │    - Resolve PreKey bundle   │                                  │
     │      for each recipient      │                                  │
     │    - Advance Double Ratchet  │                                  │
     │    - Encrypt content →       │                                  │
     │      ciphertext blob         │                                  │
     │                              │                                  │
     │ 2. message:e2e:send ────────→│                                  │
     │    {channelId, clientMsgId,  │                                  │
     │     ciphertext,              │                                  │
     │     senderDeviceId}          │                                  │
     │                              │ 3. Auth + Rate Limit Check       │
     │                              │ 4. Idempotency Check (Redis)     │
     │                              │ 5. Store ciphertext as-is        │
     │                              │    INSERT INTO messages          │
     │                              │    (content = encrypted blob)    │
     │ 6. message:ack ─────────────│                                  │
     │    {messageId, status:      │                                  │
     │     "sent"}                  │                                  │
     │                              │ 7. message:e2e:new ─────────────→│
     │                              │    {ciphertext blob,             │
     │                              │     senderDeviceId}              │
     │                              │                                  │
     │                              │    ⚠ Server NEVER decrypts      │
     │                              │    ⚠ No bot dispatch possible    │
     │                              │    ⚠ No server-side search       │
     │                              │                                  │
     │                              │ 8. Client decrypts locally:      │
     │                              │    - Lookup session by           │
     │                              │      senderDeviceId              │
     │                              │    - Decrypt with Double Ratchet │
     │                              │    - Render plaintext            │

    主要特征：

    • 所有加密/解密都发生在使用共享 packages/signal 库的客户端上。
    • 服务器是一个盲中继：它存储和转发不透明的密文 blob。服务器无法读取消息内容，也无法进行端到端通道的全文检索。
    • 仅通过元数据强制读取一次/消失消息：读取确认、到期时间戳和逻辑删除状态。当策略过期时，客户端必须删除本地明文。
    • 机器人 不能 参与 E2E 渠道——这是一种架构权衡。 E2E 协议没有在不破坏端到端保证的情况下在棘轮中包含第三方密钥的机制。
    • 密钥材料（PreKey 捆绑包、签名预密钥）存储在服务器端专用的 signal_key_bundles 表中，但私钥永远不会离开客户端。
    • 密钥分发、群发消息（Sender Key）、设备多会话管理等详细信息请参见Security & E2EE Roadmap。

    主要特征：

    • 斜杠命令是交互事件 (bot.command.invoke)，默认情况下不是持久的用户消息。如果需要审计跟踪，服务器在接受命令后会创建单独的 system 消息或审计日志条目。
    • 机器人命令通过 Redis Streams 传递到机器人引擎，将请求-响应生命周期与主消息管道解耦。
    • 每个安装的机器人都维护与机器人引擎的持久 WebSocket 连接。命令和响应流经此专用通道。
    • 机器人响应作为常规消息（带有 botId 属性）注入回通道，对所有通道成员可见。
    • 机器人SDK设计、事件订阅模式和安全约束请参见Bot Engine Research。

    • 完成后，stream_end 提供最终的令牌使用统计信息（promptTokens、completionTokens、totalTokens）。
    • 工具调用（Web 获取、代码沙箱、SDK API）作为特殊块类型在流中交织。

    附录：关键架构决策日志¶

    决定 理由 日期
    荣誉超过 Fastify/NestJS 冷启动<50ms，跨运行时，内置中间件，测试简单。如果排除无服务器，Fastify 是后备方案。 2026-06-24
    基于原始 WS/uWS 的 Socket.IO 房间管理、重新连接、心跳、用于水平扩展的 Redis 适配器 - 全部内置。与第一阶段的原始吞吐量相比，操作简单。 2026-06-24
    基于 Kafka/NATS 的 Redis 流（第 1 阶段） 零额外基础设施成本（Redis 已部署）。消费者群体足以满足早期机器人引擎的需求。为阶段 2 定义的 NATS JetStream 升级路径。 2026-06-24
    Zustand 超过 Redux/Jotai 轻量级、选择器精度、基于Map的标准化存储、中间件生态系统。适合IM的高频状态更新。 2026-06-24
    react-virtuoso 优于 tanstack/react-virtual 内置双向无限滚动、自动跟随输出、粘性标题——所有这些都是聊天消息列表所必需的。 17KB 捆绑成本可以接受。 2026-06-24
    UUID v7 优于 UUID v4 按时间排序的 ID 支持单字段游标分页 (WHERE id < cursor ORDER BY id DESC)，从而无需使用 (created_at, id) 复合游标。 2026-06-24
    消息内容的 JSONB 多态内容（文本、图像、文件、系统）自然映射到 JSONB。 PostgreSQL JSONB 支持附件类型查询的索引（@> 包含）。 2026-06-24
    每通道加密模式 工作区可以混合普通通道和端到端通道。这避免了全有或全无的权衡，并允许用户为每个对话选择适当的安全模型。 2026-06-24
    单体优先部署 所有服务都位于第一阶段，代码中具有明确的域边界。服务拆分推迟到规模需要时进行，从而避免过早分配复杂性。 2026-06-24
