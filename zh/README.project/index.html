    Nexus 聊天¶

    具有混合加密的类似 Slack 的工作区聊天系统：支持机器人、消息历史记录和服务器端工作流程的正常通道，以及服务器只能看到密文的端到端加密 DM。使用 React、Electron、Hono 和 Socket.IO 使用 TypeScript 从头开始​​构建。

    第一阶段提供了一个带有 Web 客户端、Electron 桌面 shell、TUI/CLI、REST/WebSocket 网关、完整消息状态机、带有 SDK 的机器人引擎、三个第一方机器人、Signal 式 E2E 服务边界、用于 1:1 E2EE DM 的机会性 WebRTC P2P 直接连接、表情符号反应、消息回复/转发/上下文菜单和实时状态的单一存储库。该测试套件涵盖 18 个文件、87 个测试，语句、函数和行覆盖率为 100%。

    加密模型¶

    每个通道和 DM 独立选择其加密级别。没有全局切换。

    模式 服务器端内容 允许机器人 服务器搜索 留言功能
    正常 明文 是的 未来（第二阶段） 完整：反应、编辑、删除、转发、保存、已读回执
    E2EE 仅密文 否 — 在网关被拒绝 已禁用 减少：只读一次、TTL 过期、删除时墓碑化

    关键设计特性：

    • 加密模式按通道存储在数据库中。客户端和服务器在通道创建时就这一点达成一致。
    • E2EE通道仅接受content.type === "ciphertext"。任何发送到 E2EE 通道的普通明文消息都会返回 VALIDATION_FAILED。
    • 机器人无法加入E2EE频道。如果机器人尝试加入、安装到 E2EE 通道或向 E2EE 通道发送消息，服务器将返回 E2E_BOT_NOT_ALLOWED。
    • E2EE 通道的所有机器人事件（bot.command.invoke、message.created）均被抑制 — 机器人引擎在 channel.mode === "e2e" 时跳过调度。
    • E2EE附件元数据也被门控：加密文件必须携带scanStatus: "skipped"。未跳过的 E2EE 附件将被拒绝。

    阶段 1 中的数据层： 域服务使用内存存储（基于Map）。完整的 PostgreSQL 模式（17 个表，Drizzle ORM）和 Redis 基础设施是通过迁移定义和验证的，但运行时存储层尚未连接到 Postgres。 SESSION_STORE=redis 路径通过 RedisRefreshSessionStore 执行 Redis 支持的刷新会话。

    正常消息发送的数据流：

    1. Web 客户端通过 Socket.IO 发出 { type: "message.send", payload: { workspaceId, channelId, clientMsgId, content } }。
    2. 网关根据 Zod 模式验证 WS 信封和内部负载。
    3. messageService.send() 检查通道访问、模式兼容性、幂等性 (clientMsgId) 和附件有效性。
    4. 使用 id (UUID v7)、状态 "sent" 创建一条新消息，并将其存储在内存中。
    5. 如果通道正常，botService.publishEvent({ type: "message.created", ... })会调度到订阅的机器人。
    6. 网关向频道房间内的所有客户端广播{ type: "message.created", payload: message }。
    7. 客户端通过{ type: "message.ack", payload: { messageId } }确认。
    8. 已读收据缓冲在内存中并批量刷新（设计中为 3 秒窗口，在第一阶段立即执行）。

    快速入门¶

    先决条件： Node.js >=22、pnpm 9.15.x、Docker。

    pnpm install
cp .env.example .env
docker compose up -d
pnpm db:migrate
pnpm db:seed
pnpm dev

    服务器在 http://127.0.0.1:4000 上启动，Web 客户端在 http://localhost:5173 上启动。

    Docker 还可以运行 API 服务器和构建的 Web 客户端：

    docker compose up -d --build server web

    Web 容器侦听 http://127.0.0.1:5173。对于 LAN 访问，请使用浏览器可以访问的 API URL 重建 Web 映像：

    VITE_API_BASE=http://192.168.1.20:4000 docker compose up -d --build web

    种子凭证：

    电子邮件 密码
    ada@example.com Password12345!
    grace@example.com Password12345!

    您还可以直接在网络应用程序中或通过 API 注册用户。有关故障排除的详细分步指南，请参阅 QUICKSTART.md。

    消息生命周期¶

    状态机¶

    DRAFT ──→ SENDING ──→ SENT ──→ DELIVERED ──→ READ
                        │
                        └──→ FAILED (retry ≤3, exponential backoff)
                              └──→ DELETED (tombstone)

    幂等性¶

    每条消息都带有一个clientMsgId（客户端生成的唯一字符串）。服务器存储(senderId, clientMsgId)映射。重复发送返回现有消息 - 没有重复行，没有重播副作用。

    分页¶

    消息按(channel_id, created_at DESC, id DESC)排序。 API 使用基于游标的分页，消息 id 作为游标。这可以避免新消息到达时的偏移漂移。

    已读回执¶

    已读回执 (message.ack) 缓冲在内存中。该设计要求 Redis 刷新窗口为 3 秒；第一阶段通过messageService.flushReadReceipts()实现立即刷新。

    E2EE 消息处理¶

    • 只读一次： 当带有 readOnce: true 的密文消息被确认时，它会立即被逻辑删除（type: "tombstone"、reason: "read_once_consumed"）。
    • TTL 过期： messageService.cleanupExpiredMessages() 扫描超过其 expiresAt 的密文消息，并将其替换为 reason: "expired" 逻辑删除。
    • 定期删除： softDelete 生成 reason: "deleted" 墓碑。原始密文永远不会泄露。

    机器人框架¶

    架构¶

    机器人通过机器人特定的令牌身份验证连接到专用的 /bots Socket.IO 命名空间。命名空间运行事件轮询循环（500 毫秒间隔），将待处理事件推送到连接的机器人。

    生命周期¶

    1. 安装： POST /api/v1/bots/install 以及清单。返回 nxbot_v1_... 令牌。
    2. 频道会员： POST /api/v1/bots/:botId/channels/:channelId。机器人必须具有 channels:read 范围。
    3. 事件订阅： POST /api/v1/bots/subscriptions?eventType=message.created。订阅的事件通过 dispatchToBots 调度。
    4. 消息发送： 机器人使用其令牌调用 POST /api/v1/bots/messages。服务器验证范围 (messages:write)、通道成员资格和 E2EE 限制。

    机器人 SDK¶

    import { NexusBotClient } from "@nexus-chat/bot-sdk";

const bot = new NexusBotClient({
  baseUrl: "http://127.0.0.1:4000",
  token: "nxbot_v1_...",
  manifest: {
    id: "my-bot",
    name: "MyBot",
    commands: [{ name: "/echo", description: "Echo input" }],
    scopes: ["commands:handle", "messages:write"]
  }
});

bot.use(async (event, next) => { /* middleware */ await next(); });
bot.onCommand("/echo", async (event) => { /* handle command */ });
bot.onEvent("message.created", async (event) => { /* handle event */ });
bot.connect();

    SDK功能： - 自动重新连接，具有指数退避和抖动（最多 10 次重试，1 秒至 30 秒窗口）。 - 带有 use() 的中间件管道。 - 类型安全的 sendMessage()、getChannelInfo()、subscribe()/unsubscribe() REST 帮助程序。 - redactToken() 用于日志安全的实用程序。

    内联/help¶

    服务器无需连接机器人客户端即可处理 /help。 botService.invokeCommand 检测 command === "/help"，查找其清单声明 /help 命令的任何已安装机器人，生成列出所有命令的响应消息，并将其广播到频道。即使没有机器人连接到/bots，这也可以工作。

    事件类型¶

    活动 触发
    bot.command.invoke 用户通过 WS 发送斜杠命令
    message.created 发送正常模式消息
    workspace.member_added 成员加入工作区

    E2EE设计¶

    服务边界¶

    apps/server/src/domain/signal/service.ts 中的 signalService 提供服务器端预密钥基础结构：

    • 上传捆绑包： 存储身份密钥、签名预密钥和可选的一次性预密钥。
    • 获取捆绑包： 检索预密钥捆绑包并以事务方式使用一个一次性预密钥。
    • 使用一次性预密钥： 将特定 OPK 标记为已使用（幂等；如果已使用，则返回 CONFLICT）。
    • 会话存储： 存储链接到所有者和对等用户 ID 的 Signal 会话。

    客户端外观¶

    packages/signal 提供了带有 generateIdentity、generatePreKeyBundle、encryptMessage 和 decryptMessage 的本地外观。这用于测试和烟雾脚本。生产信号协议集成 (@signalapp/libsignal-client) 是针对许可影响进行评估的 AGPL-3.0 依赖项。

    E2EE 通道限制¶

    • 仅接受content.type === "ciphertext"。
    • 机器人在网关、服务和渠道会员级别被拒绝。
    • 附件必须带有scanStatus: "skipped"——无服务器端病毒扫描。
    • E2EE 通道的服务器端消息事件 (message.created) 被抑制。

    P2P直连¶

    1:1 E2EE DM 使用 WebRTC 数据通道伺机绕过服务器。服务器仅中继 SDP/ICE 信令，而不中继消息数据。

    Alice ═══ WebRTC Data Channel ═══► Bob     (preferred, DTLS + Signal encrypted)
  │                                  │
  └── WebSocket signaling ──► Server ◄── signaling reply ──┘

    连接策略：

    1. 发送 E2EE DM 时，客户端会检查与对等方的活动 WebRTC 连接。
    2. 如果不存在，则启动 WebRTC 握手：SDP Offer/answer + ICE 候选者通过服务器 WebSocket 信令（p2p.offer、p2p.answer、p2p.ice-candidate）交换。
    3. 如果连接在 5 秒内成功 → 消息通过数据通道流动。
    4. 如果 WebRTC 失败（NAT/防火墙）→ 透明回退到现有服务器中继的 WebSocket 路径。
    5. 尝试失败后，对等方会进入 30 秒的冷却期，然后再重试。

    关键属性：

    • 无 npm 依赖项 — WebRTC 是浏览器原生的（RTCPeerConnection、RTCDataChannel）。
    • 双重加密：DTLS（传输）+信号协议（应用）。
    • 服务器永远不会看到 P2P 消息内容、时间戳或计数 — 只能看到信令元数据。
    • TUI/CLI 客户端保持仅中继（Node.js 缺乏本机 WebRTC）。

    实现： apps/web/src/lib/p2p/ - P2pConnectionPool，HybridTransport，信令处理程序。

    安全¶

    层 实施
    密码哈希 Argon2id (memoryCost: 65536, timeCost: 3, parallelism: 4)
    访问令牌 JWT RS256，15 分钟到期，sub 索赔
    刷新令牌 不透明nxrefresh_...、7天有效期、一次性轮换、重放检测
    会话后端 InMemoryRefreshSessionStore (dev) 或 RedisRefreshSessionStore
    速率限制 每IP登录速率限制器+每用户WS事件限制器（50个事件/10秒）
    跨域资源共享 通过 WEB_ORIGIN
    安全标头 X-Content-Type-Options、X-Frame-Options、Referrer-Policy、X-XSS-Protection
    日志编辑 Pino 密文、令牌、密码编辑
    审计追踪 针对身份验证、工作区、通道、机器人和附件操作的内存审核事件

    已知限制¶

    第一阶段是本地开发和内测里程碑。主要限制：

    • 内存存储： 域服务使用基于 Map 的状态。 PostgreSQL 模式和迁移已定义，但运行时持久层未连接。 Redis 可通过 SESSION_STORE=redis 进行会话存储。
    • 单设备 E2EE： 每个用户一台设备。多设备支持和组 E2EE（发送方密钥）被推迟。
    • 无全文搜索： 消息搜索仅限于基于光标的分页。 tsvector 索引计划在第二阶段进行。
    • 无 WebSocket 水平缩放： Socket.IO 在开发中无需 Redis 适配器即可运行单进程。
    • 电子打包： 无生产代码签名、公证或自动更新发布。
    • 附件用户体验： 服务器端附件原语存在；未构建网络/桌面上传 UI。
    • P2P 客户端支持： 基于 WebRTC 的 P2P 直接连接可在 Web（浏览器）和 Electron 客户端中使用。 TUI/CLI 仍然仅用于服务器中继（Node.js 缺少原生 RTCPeerConnection）。

    完整列表请参见docs/known-limitations.md。
