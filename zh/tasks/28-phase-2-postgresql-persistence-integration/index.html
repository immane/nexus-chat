    28 - 第 2 阶段 - PostgreSQL 持久性集成¶

    目标¶

    通过 Drizzle ORM 将服务器的仅运行时 InMemoryStore 作为生产事实来源替换为 PostgreSQL，同时保留内存中持久性实现以供显式开发和单元测试使用。

    迁移必须是增量的、事务安全的并且每个域切片都是完整的。生产配置绝不能默默地回退到内存持久性。

    当前状态¶

    apps/server/src/db/schema.ts、初始 Drizzle 迁移、db/client.ts 和种子脚本已存在。运行时身份验证、工作区、通道、消息、附件、机器人和信号服务仍然直接改变单例 InMemoryStore。

    现有模式还不能代表所有运行时状态。在生产中选择适配器之前，迁移必须涵盖通道创建者/描述/软删除数据、消息回复和转发元数据、保存、读取回执、引脚、静音和文件通道关联。

    范围¶

    28.1 PostgreSQL 运行时基础设施¶

    • 在 docker-compose.yml 中启用 PostgreSQL 和 Redis 服务、运行状况检查和持久 PostgreSQL 卷。
    • 将PERSISTENCE=memory|postgres添加到apps/server/src/config/env.ts。
    • 仅在开发和测试中默认为 memory。
    • 当NODE_ENV=production时拒绝PERSISTENCE=memory。
    • 仅当选择 PostgreSQL 持久化时才延迟初始化 pg.Pool。
    • 添加数据库活跃/就绪帮助程序，并在 HTTP 服务器正常关闭后关闭池。
    • 将迁移执行保持为 CI/CD 或显式一次性操作。 DB_MIGRATE_ON_BOOT=true 可能仅支持本地开发。
    • 添加 /readyz 以配置 PostgreSQL 和 Redis 依赖准备；保留 /healthz 以保证进程的活跃度。

    28.2 模式奇偶校验和迁移验证¶

    • 在实现适配器之前将 apps/server/src/db/schema.ts 与活动的共享域合约协调起来。
    • 添加新生成的 Drizzle 迁移，而不是修改现有的基线迁移。
    • 保留通道createdById、description和deletedAt。
    • 保留消息replyToMessageId、originalSenderId和originalCreatedAt。
    • 添加已保存消息、消息已读回执、频道 pin 和每用户频道静音的关系记录。
    • 添加与FileRecord匹配的文件channelId表示。
    • 定义一种持久的每通道读取状态表示。它必须匹配公共 API 语义并替换 channelLastRead 作为仅用于生产的事实来源。
    • 添加显式的行到域映射器。 PostgreSQL Date 值必须成为共享合约中使用的 ISO 字符串； Drizzle 行类型不得逃避持久性适配器。

    28.3 持久化端口和组合根¶

    • 仅在迁移其消费服务时引入异步、查询形状的持久性端口。
    • 通过工厂/组合根为每个迁移的服务提供所需的端口；不要直接从服务代码导入 db、Drizzle 表或 store。
    • 在为该服务选择 PostgreSQL 适配器之前，先实现内存适配器和 PostgreSQL 适配器。
    • 保持接口特定于领域。例如，消息持久性公开 listPage、幂等消息查找和事务消息创建，而不是通用 Map 样式的 getter/setter。
    • 将事务边界置于完整的服务用例周围，而不是单个存储库调用。
    • 不要创建通用 CRUD 存储库、全局存储库注册表或在运行时抛出的占位符 PostgreSQL 适配器。

    28.4 垂直迁移顺序¶

    1. 授权
    2. 迁移用户和审核记录。
    3. 保留现有的刷新会话内存/Redis 抽象；持久性选择不得隐式更改它。

    4. 更新身份验证路由和调用者以等待迁移的服务。

    5. 工作空间和频道

    6. 迁移工作区、成员资格、频道、频道成员资格、频道更新、静音和确定性 DM。
    7. 使工作区创建、DM 创建和成员删除成为事务性的。

    8. 将 store 上的 WebSocket 房间引导扫描替换为服务级别访问查询。

    9. 消息

    10. 迁移消息、幂等性、回复/转发元数据、反应、保存的消息、pin、读取状态、收据和附件关联。
    11. 使用数据库唯一的(sender_id, client_msg_id)约束实现幂等性；如果发生冲突，则返回现有消息。
    12. 保留光标分页顺序和 API 行为。

    13. 更新 REST 和 WebSocket 路径以等待消息服务。

    14. 附件、信号和机器人

    15. 保留附件元数据和上传会话生命周期；保留仅用于开发的字节Map，直到引入对象存储为止。
    16. 迁移信号包、一次性预密钥和不透明会话元数据。在带有 FOR UPDATE SKIP LOCKED 的事务中使用一次性预密钥。

    17. 迁移机器人安装、会员资格和订阅。在多实例部署之前，将机器人待处理事件传送从内存阵列移至 Redis Streams 或 BullMQ。

    18. 从生产路径中删除存储

    19. 限制 InMemoryStore 导入到内存适配器、测试实用程序以及明确仅用于开发的文件字节处理。
    20. 验证每个生产持久数据路径都使用 PostgreSQL。

    28.5 操作状态边界¶

    PostgreSQL 存储库端口不得表示以下内容：

    • 在线连接计数和输入指示器：单节点阶段的进程本地状态，然后是 Redis。
    • 身份验证和 WebSocket 速率限制存储桶：Redis。
    • 机器人待处理事件传送：Redis Streams 或 BullMQ。
    • 短期读回执批处理缓冲区：通过持久消息/读状态持久性刷新 Redis 或进程本地缓冲区。
    • 开发上传/下载文件字节：仅开发地图；生产文件字节属于对象存储。

    非目标¶

    • 没有按服务划分数据库。
    • 没有 Redis 缓存、Socket.IO 适配器、BullMQ 或对象存储生产超出持久性所需的范围。
    • 每个应用程序副本不会自动执行生产迁移。
    • 在存在等效的 PostgreSQL 适配器集成覆盖范围之前，不会删除内存适配器。
    • E2EE 加密操作或加密有效负载语义没有变化。
    • 没有模糊授权和域不变量的通用数据访问层。

    验收标准¶

    • [ ] NODE_ENV=production 在启动配置验证期间拒绝 PERSISTENCE=memory。
    • [ ] PERSISTENCE=memory 不实例化 PostgreSQL 池。
    • [ ] PERSISTENCE=postgres 当 PostgreSQL 无法访问时，在提供流量之前准备就绪失败。
    • [ ] Docker Compose 启动 PostgreSQL 和 Redis，并通过健康检查和持久 PostgreSQL 卷。
    • [ ] 干净的 PostgreSQL 数据库应用所有生成的迁移并接受种子脚本。
    • [ ] 架构迁移包含每个迁移的生产服务片使用的每个字段和关系。
    • [ ] 每个迁移的服务都有完整的内存和 PostgreSQL 适配器；没有选定的 PostgreSQL 存根。
    • [ ] 工作空间创建、确定性 DM 创建、成员删除、带有附件关联的消息创建以及信号一次性预密钥消耗都是原子的。
    • [ ] 使用相同的 (senderId, clientMsgId) 发送重复的并发消息，返回一条持久消息。
    • [ ] 并发信号包获取不能使用相同的一次性预密钥。
    • [ ] 没有从 InMemoryStore 读取生产配置的持久数据路由、网关路径或套接字引导路径。
    • [ ] 现有单元测试以内存持久性方式运行； PostgreSQL 适配器和路由集成测试针对一次性 PostgreSQL 运行。
    • [ ] pnpm lint、pnpm typecheck、pnpm test 和 pnpm build 通过。

    测试计划¶

    • 针对空的一次性 PostgreSQL 实例运行迁移和种子数据。
    • 验证开发/测试内存模式和仅生产 PostgreSQL 模式的环境验证。
    • 测试每个持久性适配器的域映射、约束和事务行为。
    • 测试重复消息发送、并发 DM 创建、工作区创建回滚以及并发一次性预密钥消耗。
    • 针对 PostgreSQL 执行迁移的 REST 和 WebSocket 路径；验证广播保留其当前的有效负载。
    • 保留规则和边缘情况的快速内存服务单元测试。
